### Gotchas / lecciones

- **`to_rfc3339()` ≠ `serde_json` para `DateTime<Utc>`**: `to_rfc3339()` emite `+00:00` pero `chrono`
  con `serde` emite `Z`. La forma equivalente es `to_rfc3339_opts(SecondsFormat::AutoSi, true)`; el
  test lo fija. Sustituir una por otra sin test cambiaba el contrato JSON.
- **Un `.expect` puede esconder un fallo real tras la API fluida**: `Response::builder().header(..)` no
  falla en el sitio, sino al llamar a `.body()`. En `storage.rs` el valor que podía romperlo era el
  `mime` procedente de la base → **no** era un builder infalible (corrige la hipótesis `FP-S3` para
  `reqwest::Client::builder().build()`: inicializar el backend TLS sí puede fallar).
- **`.gitignore` demasiado amplio huérfana infraestructura en silencio**: `/scripts/*` dejó el
  generador del lock fuera de Git y el gate quedó irrecuperable sin señal clara.
- **Un cambio de versión de la herramienta reabre proyectos cerrados**: el mismo árbol pasó de «0
  errores» (0.7.7) a 17 errores (0.7.8). Toda cifra debe viajar con versión/commit del binario.

### Lecciones

- Un `timeout` de runner **por debajo** del timeout interno de un test es invisible: el test declara
  cuánto se concede y muere antes por el techo del runner. Ante «Timeout of Xms exceeded» en un test de
  fixture, comparar X con los timeouts internos del test **antes** de tocar el código.
- `mocha <archivo>` con un `spec` en `.mocharc.json` ejecuta **toda** la suite: el `spec` del config
  manda y los argumentos posicionales no lo acotan.
- Nunca canalizar mocha por `Select-String`: el buffer se traga la salida y «no output» parece un
  cuelgue cuando en realidad está corriendo. Redirigir a fichero y leer la cola.

- **Un backlog de FPs citado por `archivo:línea` caduca.** Hay que re-medir con el artefacto que el gate
  ejecuta de verdad: el binario instalado y el checkout pueden divergir y las reglas cambian entre
  versiones. Los tres diagnósticos del plan eran total o parcialmente obsoletos.
- **`timeout` de runner es un suelo, no un techo configurable hacia abajo.** Un override local menor
  endurece el límite sin avisar: es la causa de los 3 ficheros con 30 s.
- Un test **carga-intermitente** no se arregla declarándolo verde: hay que darle margen real, porque su
  fallo bajo carga hace fallar `quality:setup` —y con él, la evidencia de release de todos los consumidores.
- Contar `✓` en un log **en curso** produce diagnósticos falsos: parecía una ejecución aislada de 442 tests
  cuando `mocha <archivo>` estaba corriendo la suite completa. Verificar tamaño del log y `N passing` final.

## Bloque 1.E — Plan `109A-9`: certificación compartida del gate + skills

**Origen:** pregunta del usuario tras el release 0.7.9 — «¿hay que hacer eso cada vez que se suba una
versión nueva de Sentinel? ¿no habíamos hecho algo para centralizar la versión de Sentinel?», seguida de
«planifica bien eso, incluyendo actualizar las skills si es necesario para que no se vuelva a perder
tiempo así».

**Hallazgo central: la centralización sí existía, pero solo como guarda, nunca como escritor.**
`npm run sync:quality` (`workspace-manager/scripts/quality-sync.mjs`) recorre los consumidores y exige que
el `commit` de cada `quality-tools.json` coincida con el HEAD del checkout compartido
(`area-trabajo/.quality-tools/{sentinel,varsense}`); es read-only y fail-closed (0 ok / 1 desync /
2 error de entorno). `verificar-alineacion.mjs` añade la alineación triple pin/runtime/publicado. Lo que
**nunca se construyó** es el escritor (`quality:bump`): por eso la propagación se hizo editando 11
manifiestos a mano. El defecto real no es falta de centralización, sino su asimetría.

**Coste medido** (`quality:setup`, lote 0.7.9): GLORYINSPECTOR 248 s, freebuff-bridge 255 s, GLORYPORT
271 s, coolify-manager-rs 382 s, Glory-Laminal 407 s ⇒ **~5 min por proyecto y 42–55 min por lote**, casi
todo el mismo `compile` + suite del **mismo commit** repetido 8–11 veces. Dos campañas (0.7.8 + 0.7.9)
≈ **2 h de CPU para certificar 2 commits**.

**Contrato que lo explica:** `releaseEvidence()` (`glory-sentinel/src/core/diagnose.ts:253`) exige
`commit === commit && compile === 'passed' && suite === (testScript ? 'passed' : 'not-configured') &&
cleanStaging === true`. La evidencia está indexada por `(tool, commit)`: el archivo de cada consumidor es
un **duplicado local de un hecho global**.

**Dato que reencuadró el trabajo:** los 8 `scripts/quality/quality-setup.mjs` de la familia A son
**byte-idénticos** (sha `CD1BB00CB0DE`, 81 líneas) salvo PROYECTO TASKS (`E901DDA63288`). Cachear antes de
unificar habría nacido duplicado 8 veces ⇒ el plan fija el orden **adapter único primero, caché después**.

### Incidente del escritor (costó ~40 min y dejó 7 reglas)

`bump --tool sentinel --write` escribía shims **también en modo pin**. En el host la ruta del shim
**coincide con el adapter canónico**, así que el adapter quedó sustituido por un shim que delegaba en sí
mismo (recursión) y los 9 consumidores apuntaron al archivo roto. El síntoma engañaba:
`AssignProcessToJobObject: (50)` + exit `-2147483645`, que parecía un problema de `spawn`/`windowsHide`;
se descartó midiendo los 4 combos de opciones (todos status 0). Recuperación: el adapter desde el
**historial local del editor** (archivo nuevo, sin commitear, así que Git no lo tenía) y
`lock-generator.mjs` desde Git.

Correcciones: `escribirRouters = soloShims && escribir` (el modo pin solo reporta); invariante del host
(estado `host`, nunca se escribe); guard de recursión en el shim (falla explícito en vez de delegar en sí
mismo); `ausente` + `--write` ahora crea el shim; el adapter falla con mensaje claro (exit 2) si falta el
manifiesto. Fijado con `bump.test.mjs` (**4/4**): el host nunca se reescribe, un dry-run no toca archivos
y los canónicos siguen siendo adapters.

### Segundo hallazgo del cierre (2026-09-11): presupuesto del runner de staging
El `setup` de `WANDORIUS` abortaba a mitad **sin escribir evidencia**. Causa: el runner aplicaba un
presupuesto fijo de **300 s** a instalar, compilar y ejecutar la suite en staging aislado, mientras la
suite de Sentinel hace I/O real (git, worktrees) con duración **carga-intermitente**: 180 s medidos en
una corrida y 344 s sin terminar en otra. **El presupuesto es un suelo del runner, no un techo del test.**
Fix: `STAGE_TIMEOUT_MS = 900_000` declarado explícito **solo** para las tres etapas de staging; los
defaults de `run()` siguen en 300 s para el resto de invocaciones. Resultado: `quality:setup` **exit 0 en
464,6 s** con evidencia de `sentinel@a3f5607` y `varsense@21d8a70`; `doctor` **0 issues**, `readyForGate: true`.

### Regresión detectada y restaurada (mismo cierre)
El working tree de `WANDORIUS/scripts/quality/setup.mjs` había **revertido el fix de `tar` de `318A-4C`**
(HEAD usa la ruta relativa `..\<basename>`, que elimina la ambigüedad para GNU tar y bsdtar; el working
tree había vuelto a la variante absoluta anterior). Se restauró la versión commiteada conservando **solo**
el cambio de presupuesto: el diff final es exactamente eso (`git diff` verificado). **No se silenció.**

### Lección
Antes de construir una capacidad nueva, comprobar si la **guarda** ya existe y lo que falta es el
**escritor**. Y un escritor que puede tocar el archivo del que él mismo vive necesita un **invariante
explícito**: separar «reportar» de «escribir» no es una opción de diseño, es la única versión segura.
