## 318A-8: la config del agente (modelo/modo) se guarda y se recarga por conversación

**Reporte del usuario:** "la selección de modelo no se guarda al recargar; todas las
configuraciones deben guardarse incluyendo el modo de operación".

### Causa raíz

El selector de modelo/modo del input (`PanelAgente.tsx`) y el modal (`ModalConfigAgente.tsx`)
leían la config **global** del store (`useAgenteStore(s => s.config)`, inicializada desde
`localStorage['glory-agente-config']`), mientras que **cada conversación** guarda su propia config
en el servidor (columna `config` + `modo` de `agente_conversaciones`, persistidas por
`guardar_config_conversacion` desde 318A-4). Con una sola conversación coincidían y no se notaba;
con varias, al recargar la página la tab activa podía tener una config distinta a la del
localStorage y el selector mostraba la equivocada (la del localStorage, de otra conversación).
Además `establecerConfig` usaba la global como base, arrastrando valores ajenos a la conversación
activa.

### Qué se hizo (frontend, `frontend/src/app/plugins/agente/store.ts`)

1. **Nuevo helper `configDeTab(estado, id)`**: devuelve la config de la tab indicada, con fallback
   a la global (fuente de verdad = config de la conversación activa).
2. **`cargarConversaciones`**: al cargar la lista, la config global se alinea con la de la
   conversación activa (si hay conversaciones); si no hay, conserva la del localStorage.
3. **`abrirTab`**: al cambiar de conversación, sincroniza `config` global con la config de ESA
   conversación (persistida en servidor).
4. **`cerrarTab`**: al cerrar la tab activa, alinea la config con la nueva tab activa; si no queda
   ninguna, vuelve a la del localStorage (defaults).
5. **`establecerConfig`**: la base pasa a ser la config de la tab activa (no la global), de modo
   que cada conversación conserva sus propios valores y se persisten en el servidor + localStorage.

No se tocó backend: `guardar_config_conversacion` ya persiste `config` + columna `modo`, y
`config_desde_guardada` ya lee `provider`/`modelo` de la config guardada (318A-4).

### Verificación

- `npm run type-check` exit 0; `npm run build` exit 0 (solo warnings preexistentes de chunk size).
- Navegador (usuario admin, dev server Vite 5175 + backend 3001):
  1. Con 2 conversaciones (configs distintas), al **recargar** con la tab activa `groq/compound-mini`
     el selector mostraba antes "GLM 5.3 Flash" (incorrecto) y ahora **"Compound Mini" + "Meta"** ✓.
  2. Al **cambiar de tab**, el selector se actualiza a la config de esa conversación ✓.
  3. Al **cambiar modelo** (a DeepSeek V4 Flash) en una conversación y **recargar**, el selector
     muestra "DeepSeek V4 Flash" + modo correcto ✓ (persistido en `agente_conversaciones.config`).
  4. El **modal** de configuración muestra la config de la tab activa (modelo + modo checked) ✓.
- Datos de prueba (conversación extra) eliminados tras la verificación.

### Pendiente real

- Ninguno funcional. La config global de `localStorage` sigue existiendo como semilla inicial para
  conversaciones nuevas (`crearTab` usa `get().config`, ya alineado con la tab activa).

## 318A-9: menús contextuales aparecían lejos del cursor (bug global)

**Reporte del usuario:** "los menús contextuales deberían aparecer justo donde se dio el click, no
alejados del cursor; pasa globalmente con la mayoría de los menús contextuales".

### Causa raíz

`MenuContextual` (y `MenuFlotante`) usan `position: fixed` con coordenadas del viewport
(`clientX/clientY` o `getBoundingClientRect`), pero se renderizaban **inline** dentro del árbol de
componentes. El wrapper de cada panel del sidebar, `.dashboardSidebarPanel--visible` en
`DashboardPanelView.tsx`, aplica `transform: translateY(0)` (y `--entrando` usa `translateY(4px)`)
para su transición de entrada. Un `transform` en un ancestro —aunque sea identidad— crea un nuevo
**containing block** para los descendientes con `position: fixed`; entonces el `fixed` deja de ser
relativo al viewport y el menú aparece desplazado (en la medición: `left/top` correctos pero
`getBoundingClientRect` desviado ~13px X / ~68px Y). Afecta a TODOS los menús montados inline
dentro de paneles del sidebar (tareas, hábitos, proyectos, notas, grupos, encabezados…).

### Qué se hizo (frontend)

1. **`MenuContextual.tsx`**: el menú raíz ahora se renderiza con `createPortal(menu, document.body)`.
   Al escapar del árbol con transform, `position: fixed` vuelve a ser relativo al viewport y el menú
   aparece exactamente donde se hizo click. **Los submenús NO se portaléan** (siguen anidados dentro
   del menú raíz): usan `position: absolute` relativo a `.menuContextualItemWrapper` y portalearlos
   los rompería (aparecen en `-162,0`).
2. **`MenuFlotante.tsx`**: mismo fix (portal a body), mismo patrón que ya usan `BottomSheet`,
   `Modal`, `SelectorGrupo`, `SelectorBadge`, `catalogoModelos`, etc.

No se perdió tema: las variables `--dashboard-*` están definidas en `:root` (`variables.css`), no en
`.dashboardContenedor`.

### Verificación

- `npm run type-check` exit 0; `npm run build` exit 0 (solo warning preexistente de chunk size).
- Navegador (usuario admin, dev server Vite 5175):
  1. **Antes**: contextmenu sobre una tarea con cursor en (226, 140) → el menú renderizaba
     `left:226px; top:140px` pero `getBoundingClientRect()` daba (238.8, 208.4): desplazado ~12px X /
     ~68px Y. El ancestro `.dashboardSidebarPanel--visible` tenía `transform: matrix(1,0,0,1,0,0)`.
  2. **Después**: mismo click → `padreEsBody: true`, `getBoundingClientRect()` = (226.2, 140.3):
     **offset 0,0 del cursor** ✓.
  3. **Submenú** (Importancia → Muy Alta): el menú raíz en body en (226,140); el submenú anidado a
     la derecha en (391,274) = borde derecho del menú (226+162) ✓, visible en pantalla ✓.
  4. **Menú de usuario** (avatar header, anclaje por `getBoundingClientRect`): aparece en body junto
     al botón ✓.
  5. Cierre con Escape y click fuera funcionan ✓.
- No se tocó backend ni CSS; cambio 100% en los 2 componentes compartidos.

### Pendiente real

- Ninguno. Si algún menú usara `position: fixed` con estilo inline propio fuera de estos 2
  componentes, tendría el mismo bug latente; hoy todos pasan por `MenuContextual`/`MenuFlotante`
  (verificados los callers de `posicionX/posicionY`).
